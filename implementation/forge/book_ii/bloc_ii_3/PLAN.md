## Governing laws (mandatory, restated)

- **IDENTITY != ENTITLEMENT.** II.3 stores who you are. It stores nothing about
  what you may access. No plan/license/entitlement/capability/product-tier
  field exists in any II.3 record, table, or principal.
- **AUTHENTICATION != AUTHORIZATION.** II.3 converts a credential into a
  verified principal. It decides nothing about access. That is II.4.
- **SESSION != LICENSE.** A session is a revocable, expiring runtime
  authentication context. It snapshots no entitlement and confers no product
  authority.
- **PROVIDER ID != FORGE ID.** The internal `user_id` is the authoritative
  FORGE identity. Provider identifiers are attributes on typed links.

Whop is NOT integrated. No provider API is called. Book VI owns commerce.

## Scope

Owns: internal FORGE user identity; user lifecycle state; external identity
links; opaque session tokens; session lifecycle (creation, expiry, revocation);
the runtime authentication boundary (credential → principal); persistence for
all of the above via the II.2 port + one forward migration.

Does NOT own: authorization (II.4), policy (II.4), product exposure (II.4),
accounts/billing/licensing (Book VI), provider adapters (II.5), Whop (Book VI),
any user-management CRUD API (not required by frozen II.3), any new public HTTP
route.

## Internal user identity

- `ForgeUserId` wraps a FORGE-generated opaque identifier:
  `uuid.uuid4().hex` (32 hex chars), generated by FORGE, never derived from a
  provider ID or an email.
- `UserState` enum: `ACTIVE`, `DISABLED` — the only lifecycle states required
  by the frozen plan. Governed transitions: `ACTIVE→DISABLED`,
  `DISABLED→ACTIVE`. Same-state and unknown transitions are illegal. No
  terminal states are invented; no elaborate lifecycle is added.
- `IdentityRole` enum: `USER`, `RESEARCH_ADMIN`, `SUPPORT_ADMIN`,
  `SYSTEM_ADMIN`, `SERVICE` (frozen Ch II.3.6). Roles are **identity
  primitives** carried on the user and the principal; they are NOT
  entitlements, are not consulted by II.3 for any access decision, and no
  generic ADMIN bypass exists. Role *enforcement* belongs to II.4.
- `ForgeUser` record: `user_id`, `state`, `roles`, optional `email`
  attribute, `created_at`, `updated_at`. `email` is an optional untrusted
  attribute: it is never a key, never unique-constrained, never used for
  lookup, and its verification belongs to later Books.
- No organization/seat modeling (Ch II.3.2 preserves the seam only — the
  `user_id` indirection is that seam).

## External identity links

- `ExternalIdentityLink` = `(provider, provider_subject) → forge_user_id`,
  with `linked_at`. Uniqueness of `(provider, provider_subject)` is enforced
  in-memory and by PK constraint in SQL.
- Multiple links (different providers) may point at one FORGE user.
- Unlinking (`delete_identity_link`) removes only the link row; the FORGE
  user survives untouched (acceptance: identity survives provider
  replacement).
- Linking rule (frozen Ch II.3.5): creating a link at II.3 requires an
  **authenticated proof** — the gateway/service accepts link creation only as
  a persistence operation; the `link_external_identity` service method
  requires an authenticated principal (or an explicitly-authorized system
  actor) and rejects a link whose `(provider, provider_subject)` is already
  bound to a *different* user (collision protection; no email-string-only
  takeover — email is never consulted in linking).
- Provider metadata carries no authorization meaning and no provider secrets
  are stored (II.3 stores no provider credentials at all).

## Principal

`ForgePrincipal` is the runtime authenticated identity context — a pure
domain value, never persisted, never HTTP-aware:

- `authenticated: bool`
- `forge_user_id: str | None` (None exactly when anonymous)
- `session_id: str | None`
- `roles: frozenset[IdentityRole]` (empty for anonymous)

It contains NO plan, license, entitlement, product tier, exposure permission,
or capability. Anonymous is a structurally distinct singleton
(`ForgePrincipal.anonymous()`: `authenticated=False`, `forge_user_id=None`,
`session_id=None`) — anonymous is never represented as a fake/persisted user
ID. II.3 defines the principal; II.4 consumes it.

## Session model

- `ForgeSessionId`: FORGE-generated `uuid.uuid4().hex`. Session ID != user ID
  != provider session ID.
- `ForgeSession`: `session_id`, `user_id` (exactly one FORGE user),
  `token_digest`, `created_at`, `expires_at`, `revoked_at` (None until
  revoked), `persisted_version`.
- Lifecycle: `created` → valid until `expires_at` unless `revoked_at` set.
  Expired ⇒ cannot authenticate. Revoked ⇒ cannot authenticate (revocation is
  permanent for that session; a new session must be issued). Disabled user ⇒
  cannot authenticate through an otherwise-valid session.
- **Expiry is absolute only.** The frozen contract (Ch II.3.4) requires
  expiration + revocation; no idle-timeout sliding expiry is introduced at
  II.3. Documented as an explicit non-feature.
- No entitlement snapshot is stored on or trusted from a session (Ch II.3.4:
  entitlements must be re-evaluable downstream — II.3 stores none).

## Session token strategy

- **Opaque bearer tokens** (frozen preference; no JWT, no signed
  self-contained tokens — nothing in the frozen architecture requires them).
- Generation: `secrets.token_urlsafe(32)` ⇒ 256 bits of CSPRNG entropy,
  URL-safe, ~43 chars.
- **Digest storage:** only `SHA-256(token)` (hex, 64 chars) is persisted.
  Raw token exists ONLY in the return value of `open_session` (the issuance
  boundary) and inside the request credential extraction moment. It is never
  stored, logged, echoed, or returned by any endpoint.
- **Secure comparison:** token lookup is by digest (deterministic SQL/
  dict lookup on the hex digest); comparisons of digests use
  `hmac.compare_digest` where equality is security-sensitive (verification
  path). Note honestly recorded: lookup by exact digest string equality
  exposes no raw-token-timing oracle because the attacker never controls a
  raw-token-bearing comparison — the digest itself is the lookup key and is
  64 hex chars of a preimage-resistant hash of a 256-bit secret; brute-force
  is infeasible without the raw token.
- **No server-side pepper.** Design decision (explicitly permitted by the
  handoff): tokens carry 256 bits of CSPRNG entropy, so the stored SHA-256
  digest is not vulnerable to offline dictionary attack; a pepper would add
  secret-management burden without a threat-model gain at II.3. Digest
  algorithm + rationale documented here and in EVIDENCE.
- Tokens encode no entitlement authority and expose no internal secrets.

## Persistence ownership

- Extends the II.2 `PersistenceGateway` port with an identity/session section.
  Domain records (`ForgeUserRecord`, `ExternalIdentityLinkRecord`,
  `ForgeSessionRecord`) live in `app/forge/persistence/records.py` (pure
  dataclasses, no DB/HTTP imports), consistent with II.2 style.
- **One new forward migration:** `002_identity_session.sql` (discovered
  automatically by the existing first-party runner). `001_initial_schema.sql`
  is ratified and executed — it is **never edited**; an executable test pins
  its SHA-256.
- Tables (portable SQL, PostgreSQL production target, SQLite contract
  executor):
  - `forge_users` — `user_id` VARCHAR PK; `state` CHECK IN
    (`ACTIVE`,`DISABLED`); `roles_json` TEXT; `email` VARCHAR(320) NULL
    (attribute only — deliberately NO unique constraint); `display_label`
    VARCHAR(200) NULL; `persisted_version` BIGINT; created/updated
    timestamps.
  - `external_identity_links` — `provider` + `provider_subject` composite
    PK; `forge_user_id` FK → `forge_users` **ON DELETE RESTRICT**;
    `linked_at`; index on `forge_user_id`.
  - `forge_sessions` — `session_id` VARCHAR PK; `user_id` FK → `forge_users`
    **ON DELETE RESTRICT**; `token_digest` CHAR(64) NOT NULL with a UNIQUE
    index (the lookup path); `created_at`, `expires_at`, `revoked_at` NULL;
    `persisted_version` BIGINT.
- **Referential integrity (conservative):** RESTRICT (not CASCADE) from
  links/sessions to users — destructive user deletion must never silently
  erase audit-relevant identity history. II.3 offers no user deletion at all:
  disable + revoke are the only removal paths.
- **No entitlement/license/plan/product tables are created.** Executable
  test asserts the migration set introduces none.

## Transaction semantics

The II.2 deferred-conflict in-memory transaction and SQL transactions are
reused unchanged. `create_user` + `create_identity_link` (+ initial session)
is one logical operation executed inside `gateway.transaction()`; a failure
anywhere rolls back ALL of it — partial identity state never survives.
`revoke_all_sessions` is a single atomic gateway operation (one UPDATE in
SQL; atomic dict sweep in-memory).

## Concurrency semantics

Optimistic concurrency (II.2 `persisted_version` + `expected_version` +
`StaleWriteConflict`) governs user-state mutation and session revocation —
newer identity state is never silently overwritten. Duplicate protection
(duplicate user, duplicate link, duplicate session, digest uniqueness)
surfaces as deterministic exceptions backed by real PK/CHECK constraints in
SQL.

## HTTP authentication boundary

- **No new public route.** The frozen II.3 objective is runtime
  authentication infrastructure; `/forge/v1/{health,ready,meta}` remain the
  only routes (route-set test continues to assert exactly 3).
- `app/forge/service/authentication.py` provides the service-layer boundary:
  `ForgeAuthenticationService.authenticate_bearer(header_value,
  allow_anonymous=...) -> ForgePrincipal` plus `open_session(user_id, ttl,
  now=...) -> IssuedSession`.
- The service is composed onto `ForgeServiceContainer` (explicit injection,
  structural port guard, no module-level singleton, purely additive field).
- Domain persistence records do not become HTTP-aware; the service converts
  credential → principal at one boundary.
- `/meta` and `/ready` are untouched; no token can flow into them (no auth
  input is read there), and tests assert a bearer header never leaks into
  those bodies.

## Authentication service behavior

Flow (Ch II.3.3 port shape, frozen): request header → extract credential →
SHA-256 digest → session lookup by digest → session-state validation (not
revoked, not expired under the injected clock) → user lookup → user-state
validation (ACTIVE) → authenticated principal with session + roles.

- No credential + anonymous allowed ⇒ anonymous principal.
- No credential + anonymous disallowed ⇒ single deterministic failure.
- Any invalid credential (malformed header, unknown token, expired, revoked,
  disabled user, dangling session) ⇒ **one** `AuthenticationFailure` whose
  message is a constant. Outcome kind is retained only as an internal
  attribute for tests/ops; the external failure is uniform — no user
  enumeration, no disabled-vs-invalid distinction, no raw DB/provider errors.
- The service performs NO authorization, plan, license, entitlement,
  capability, exposure, or product check — that is II.4/VI.

## Audit metadata & trusted vs untrusted data

- `created_at`/`linked_at` timestamps are persistence-owned audit metadata
  (UTC ISO-8601 strings, matching II.2 record style).
- Trusted: FORGE-generated `user_id`, `session_id`, digest, state, roles.
- Untrusted: `email` (attribute only, never identity, never lookup key),
  provider identifiers (attributes on links, never FORGE keys).
- Every link/unlink and state/session mutation is a deterministic,
  versioned, testable write (frozen Ch II.3.5 audit requirement met by
  versioned record history; no separate audit table is invented at II.3).

## Secret handling

- Raw tokens: never logged, never in exceptions, never in HTTP payloads,
  never in `/meta` or `/ready`, never persisted. Tests assert token absence
  in caplog records, failure messages, and meta/ready bodies.
- No pepper/secret configuration is introduced (documented decision above).
- No provider credentials, no passwords, no password-reset systems.
- Configuration: unchanged. `ForgeConfig` gains no credential fields; II.3
  needs no new env vars (TTL is a service parameter, not an env secret).

## Local/test strategy & production strategy

- Unit truth: `InMemoryPersistenceGateway` (real port implementation) +
  fixed/injectable clock ⇒ full deterministic coverage without a server.
- SQL contract truth: `SqlAlchemyPersistenceGateway` over SQLite executes
  migration 001→002 and identity round trips (dialect/schema contract only,
  same discipline as II.2).
- Production/PostgreSQL truth: CI postgres job (PostgreSQL 16 service) runs
  the existing `tests/test_forge_postgres_integration.py` **extended with an
  II.3 identity/session section** (migration chain, user/link/session
  round trips, digest lookup, revocation, constraint/concurrency behavior).
  The existing CI architecture is extended, not duplicated.
- Production deployment: identical II.2 startup path (ping → apply
  migrations → compatibility check); 002 applies after 001 with no operator
  action.
